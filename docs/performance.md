# 성능 측정

이 결과는 운영 SLA가 아니라 고정된 로컬 환경에서 같은 실행물을 다시 돌릴 수 있는 기준선입니다. 성능이 좋은 결과만 골라내지 않았으며, 30만 검색 문서에서 확인된 느린 키워드 관련도 검색도 함께 공개합니다.

## 환경

| 항목              | 값                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| host              | Apple Mac mini `Mac16,10`, CPU 10 core, memory 16 GiB                                          |
| OS                | macOS 26.0                                                                                     |
| container runtime | Colima VM 6 CPU·7.7 GiB, Docker Engine 29.2.1                                                  |
| application       | Eclipse Temurin Java 25, 2 CPU·1 GiB, heap 512 MiB                                             |
| database          | MySQL 8.4, 2 CPU·2 GiB                                                                         |
| dataset           | 300,000건, seed SQL SHA-256 `9aa73fcf46cd1332cfeff09becc8e0f77d07c70b267df9517f54e524d0836bce` |
| measured source   | commit `9d99328`                                                                               |

## EXPLAIN ANALYZE

| 조회          | 주요 실행 계획                                       | actual time |
| ------------- | ---------------------------------------------------- | ----------: |
| 키워드 관련도 | ngram FULLTEXT 후보 90,000행 후 관련도 정렬          |   약 204 ms |
| 복합 필터     | `idx_search_document_filter`, 후보 1,352행           |   약 3.0 ms |
| 최신순        | `idx_search_document_latest` covering lookup 21행    | 약 0.007 ms |
| 가격 오름차순 | `idx_search_document_price` covering range scan 21행 | 약 0.019 ms |
| 가격 내림차순 | 후보 73,872행 후 정렬                                |   약 109 ms |
| 인기순        | `idx_search_document_popular` covering lookup 21행   | 약 0.011 ms |

첫 측정에서 최신순은 `UNIX_TIMESTAMP(cataloged_at)` 계산식 때문에 30만 행을 읽어 약 3.6초가 걸렸고, 가격 오름차순은 약 104ms가 걸렸습니다. projection에 epoch 값을 함께 저장하고 `(active, cataloged_epoch DESC, product_id)`, `(active, price, product_id)` index를 추가해 위 결과로 바꿨습니다.

키워드 관련도는 9만 후보를 점수순으로 정렬합니다. 마지막 워밍 상태 측정은 약 204ms였지만, 최초 cold 측정에서는 약 1.4초가 걸렸습니다. 이 결과만으로 외부 검색엔진을 도입하지 않으며, 검색어 선택도와 pagination까지 포함한 후속 측정에서 경계를 다시 판단합니다.

원본 실행 계획은 [`performance/results/explain-analyze.txt`](https://github.com/shAn-kor/banryeo-kkurumi-backend/blob/main/performance/results/explain-analyze.txt)에 보관합니다.

## k6 혼합 검색

2분 warm-up 뒤 키워드 35%, 복합 필터 25%, 인기순 15%, 최신순 15%, 가격순 cursor 10% 비율로 10·50·100 VU를 각각 3분씩 3회 실행합니다. latency는 합격 기준으로 두지 않고 HTTP 오류·schema 오류·cursor 중복이 0인지에만 hard gate를 적용합니다.

각 값은 3회 중 중앙값이며 괄호 안은 최소~최대 범위입니다. latency 단위는 ms입니다.

10 VU에서도 키워드 관련도 요청이 포함되면서 p95가 약 3.2초였고, 50 VU부터 p50이 2초를 넘었습니다. 100 VU에서는 RPS가 오히려 감소해 이 로컬 자원 제한에서 DB 검색이 포화됐음을 보여줍니다. 이는 운영 처리량이나 SLA가 아니라 후속 개선을 비교하기 위한 재현 가능한 기준선입니다. 9개 실행의 개별 값과 분포는 [`performance/results`](https://github.com/shAn-kor/banryeo-kkurumi-backend/tree/main/performance/results)의 원본 JSON에 보관합니다.

> 이 표는 아래 [요청 비율 결함](#요청-비율-결함)이 있는 시나리오로 측정했습니다. 실제 요청 비율이 35%가 아니었으므로 수정 후 기준선과 직접 비교하지 않습니다.

## 키워드 검색 병목 조사 (#6)

[이슈 #6](https://github.com/shAn-kor/banryeo-kkurumi-backend/issues/6)에서 키워드 관련도 검색의 원인을 측정으로 확인했습니다. 원본은 [`performance/results/issue-6`](https://github.com/shAn-kor/banryeo-kkurumi-backend/tree/main/performance/results/issue-6)에 있습니다.

### 측정 환경

위 환경과 크기가 같은 Colima 전용 프로필(6 CPU·8 GiB)에서 다시 측정했습니다. Docker Engine은 29.5.2이고, 같은 seed SQL(SHA-256 `9aa73fcf…`)로 30만 건을 적재했습니다. 각 실행 디렉터리의 `environment.txt`에 commit, buffer pool 크기, 문서 수를 남깁니다.

### 요청 비율 결함

기존 시나리오는 `(__VU + __ITER) % 100`으로 요청 유형을 골랐습니다. VU 하나가 100회를 모두 돌아야 키워드 35% 비율이 맞습니다. 3분 실행에서 VU당 반복은 약 40~60회였고, 10 VU 1분 실행은 키워드 요청만 보냈습니다. 느린 설정일수록 키워드 비중이 커져 대안 비교가 왜곡됩니다.

전체 반복 번호에 100과 서로소인 37을 곱해 유형을 고르도록 고쳤습니다. 이제 연속된 100회 반복마다 각 유형이 정해진 비율로 한 번씩 나옵니다. 요청 유형별 latency와 요청 수도 함께 기록합니다. 수정 전 실행 결과는 `old-mix-*` 디렉터리에 그대로 둡니다.

### 수정 후 기준선

각 값은 3회 중 중앙값이며 괄호 안은 최소~최대 범위입니다. latency 단위는 ms입니다. buffer pool은 MySQL 기본값 128 MiB입니다.

|  VU |                RPS |                   전체 p50 |                     전체 p95 |                   키워드 p50 |                   키워드 p95 |                최신순 p50 | HTTP/schema/cursor 오류 |
| --: | -----------------: | -------------------------: | ---------------------------: | ---------------------------: | ---------------------------: | ------------------------: | ----------------------: |
|  10 |  9.75 (8.63~10.78) |           73.7 (63.9~78.3) |    3,803.1 (3,468.6~4,301.5) |    3,191.3 (2,924.7~3,491.5) |    4,233.2 (3,714.5~4,932.6) |             7.6 (5.9~8.0) |               0 / 0 / 0 |
|  50 |  9.31 (8.11~10.22) |  4,781.2 (4,206.9~5,406.0) |   9,011.1 (7,940.0~10,306.3) |    7,325.3 (6,786.7~8,512.7) |  10,420.0 (9,396.8~12,201.4) | 4,303.6 (3,879.5~4,894.8) |               0 / 0 / 0 |
| 100 | 10.01 (9.23~10.20) | 9,313.5 (9,195.8~10,296.0) | 14,012.9 (13,683.4~15,211.7) | 11,702.0 (11,682.7~12,799.6) | 17,507.1 (14,949.4~18,508.7) | 8,804.6 (8,689.9~9,596.6) |               0 / 0 / 0 |

- RPS는 VU 수와 관계없이 약 10에서 멈춥니다.
- 50 VU부터 최신순처럼 단건 1 ms 미만인 조회도 수 초가 걸립니다. 같은 시간 Hikari 대기 스레드는 50 VU에서 약 36~~41개, 100 VU에서 약 75~~91개였습니다. 키워드 쿼리가 커넥션 10개를 모두 잡아 다른 조회가 커넥션을 기다립니다.
- 10 VU 3회 동안 키워드 p50이 2,925 → 3,191 → 3,491 ms로 커졌습니다. 원인은 확인하지 못했습니다.

### 원인

- 키워드 쿼리 실행 계획에서 `Full-text index search`가 후보 90,000행을 넘기고, 그 뒤 점수와 `product_id` 순으로 정렬합니다. MySQL FULLTEXT는 후보마다 행을 읽으므로 비용이 후보 수에 비례합니다.
- 단건 실행에서는 128 MiB buffer pool이 쿼리 1회에 페이지 23,113개를 디스크에서 읽었고 약 2.2초가 걸렸습니다. 1 GiB에서는 디스크 읽기 0건, 약 254~261 ms였습니다.
- 그러나 부하 중에는 첫 1분 뒤 `Innodb_buffer_pool_reads` 증가가 0이었습니다. 부하 상황의 병목은 디스크가 아니라 2 CPU MySQL에서 9만 행을 읽고 정렬하는 CPU 작업입니다. 처음 세운 buffer pool 가설은 부하 상황에서는 맞지 않았습니다.
- 기존 표의 키워드 약 204 ms는 이번 환경의 128 MiB buffer pool에서 재현되지 않았습니다. 1 GiB에서는 같은 SQL이 약 240 ms였습니다.

### 대안 비교

설정 대안은 1분 × 1회 screening입니다. 참고용 수치이며, 1회 차이가 10% 미만이면 잡음 범위로 봅니다.

| 대안                                            | 10 VU RPS | 50 VU RPS | 결과                                              |
| ----------------------------------------------- | --------: | --------: | ------------------------------------------------- |
| 현재 설정                                       |     10.74 |     10.69 | 기준                                              |
| `innodb_buffer_pool_size` 1 GiB                 |     11.49 |     11.33 | 잡음 범위                                         |
| Hikari 최대 풀 20                               |     10.96 |     10.31 | 효과 없음                                         |
| `sort_buffer_size` 256 KiB → 8 MiB (SQL 단건)   |         - |         - | merge pass는 줄었지만 253~270 ms로 같음           |
| 검색어를 `+반려 +건강`(AND)으로 변경            |     27.08 |     26.43 | 후보 3만 행, 약 2.5배. 검색 결과가 바뀜           |
| 정렬에서 `product_id` tie-break 제거 (SQL 단건) |         - |         - | 약 10 ms. 동점 순서가 정해지지 않아 cursor가 깨짐 |

### 결정

- 설정 변경으로는 개선되지 않았습니다. 처리량을 바꾼 것은 후보 수를 줄인 AND 검색뿐이었고, 이는 검색 의미 변경입니다.
- 현재 OR 의미를 유지하면 MySQL FULLTEXT의 비용 구조를 바꿀 수 없습니다. 형태소 분석, 관련도 점수, 색인 동기화를 포함한 검색 엔진(OpenSearch) 적용을 별도 작업으로 진행합니다. 이 절의 수정 후 기준선이 그 작업의 비교 기준입니다.
- 결과 캐시와 키워드 쿼리 동시 실행 격리는 측정하지 않았습니다. 캐시는 검색어가 하나뿐인 지금 시나리오로는 적중률이 비현실적으로 높게 나오므로 검색어 분포 시나리오가 먼저 필요합니다.

## 재현

```bash
docker compose -f performance/compose.yml up -d --build
./performance/load-dataset.sh
./performance/run-explain.sh
RESULT_DIR=performance/results/<run> ./performance/run-k6.sh
RESULT_DIR=performance/results/<run> ./performance/summarize-k6.sh
./performance/sample-metrics.sh performance/results/<run>/metrics.tsv   # 측정 중 별도 터미널
```

짧은 비교 실행은 `VUS_LIST="10 50" REPETITIONS=1 DURATION=1m WARMUP_DURATION=30s`를 함께 지정합니다. 검색어는 `KEYWORD` 환경변수로 바꿀 수 있습니다.

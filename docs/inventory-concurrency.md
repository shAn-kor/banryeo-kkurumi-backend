# 재고 예약 동시성 전략 비교

[문제 해결 사례](/case-study)는 조건부 원자 UPDATE가 초과 판매를 막는다는 정합성만 확인했습니다. 이 문서는 같은 문제를 다른 세 방식과 같은 조건에서 비교해, 현재 방식을 유지할지 다시 판단합니다. 작업 기록은 [issue #9](https://github.com/shAn-kor/banryeo-kkurumi-backend/issues/9)에 있습니다.

결론은 **조건부 UPDATE 유지**입니다. Redis Lua gate는 인기 SKU 1개에 요청이 몰릴 때만 성공 처리량이 1.5~1.6배 높았습니다. 요청이 여러 SKU로 흩어지면 차이가 불명확했고, 두 저장소의 일관성을 운영하는 비용이 생깁니다.

## 비교한 전략

| 전략                   | 예약 방식                                                                                         |
| ---------------------- | ------------------------------------------------------------------------------------------------- |
| A 조건부 UPDATE (현재) | `UPDATE ... WHERE sku_id=? AND available_quantity>=?` 영향 행이 1건이면 reservation INSERT        |
| B 비관적 락            | `SELECT ... FOR UPDATE`로 행을 잠그고 수량 확인 뒤 UPDATE·INSERT                                  |
| C 낙관적 락            | `version` 조회 뒤 `UPDATE ... WHERE version=?`. 충돌하면 1~10 ms 무작위 대기 뒤 재시도, 최대 20회 |
| D Redis Lua gate       | Lua script로 Redis 수량을 원자 차감한 뒤 MySQL UPDATE·INSERT. MySQL 실패 시 Redis 수량을 되돌림   |

모든 전략은 운영 코드처럼 먼저 같은 주문의 기존 reservation을 확인하고, 수량 1개씩 예약합니다.

## 측정 조건

| 항목            | 값                                                                                                        |
| --------------- | --------------------------------------------------------------------------------------------------------- |
| hot             | SKU 1개, 재고 2,000개, 예약 시도 6,000건                                                                  |
| spread          | SKU 1,000개, SKU당 재고 50개, 예약 시도 20,000건 (run 번호를 seed로 한 균등 무작위)                       |
| 동시성          | worker 16·64, Hikari pool 크기 = worker 수                                                                |
| 반복            | 조합마다 3회. 회차마다 표를 새로 만들고 4개 전략을 교차 실행. 기록하지 않는 warm-up 선행                  |
| 환경            | Colima VM 6 CPU·7.7 GiB, MySQL 8.4.13 (REPEATABLE-READ, `innodb_flush_log_at_trx_commit=1`), Redis 7.4.12 |
| client          | host macOS의 JVM (Java 25). 측정 중 application container는 중지                                          |
| measured source | commit `eb9e423`                                                                                          |

**hard gate**는 초과 판매, 음수 재고, `available + reserved ≠ 초기 재고`, SKU별 `reserved ≠ 성공 수`, reservation 행 수 ≠ 성공 수, 재고가 남았는데 거절된 시도, Redis 수량 ≠ DB 수량입니다. 하나라도 0이 아니면 성능과 관계없이 탈락입니다.

성능은 3회 중앙값이며 괄호 안은 최소~최대입니다. 두 전략의 범위가 겹치면 "차이 불명확"으로 판단합니다.

## 결과

### hot: 인기 SKU 1개

hot은 재고 2,000개가 팔린 뒤 나머지 4,000건이 거절되는 구조입니다. 그래서 전체 시도 처리량보다 **성공 처리량**을 비교합니다.

| worker | 전략            |            성공/s | p50 ms | p95 ms | p99 ms | hard gate                |
| -----: | --------------- | ----------------: | -----: | -----: | -----: | ------------------------ |
|     16 | A 조건부 UPDATE |     373 (303~391) |    9.5 |   30.4 |   43.4 | 통과                     |
|     16 | B 비관적 락     |     321 (254~340) |    9.8 |   37.3 |   60.8 | 통과                     |
|     16 | C 낙관적 락     |     133 (133~156) |    4.4 |  231.4 |  304.9 | 통과 (재시도 소진 573건) |
|     16 | D Redis Lua     | **560 (434~574)** |    0.7 |   33.4 |   39.6 | 통과                     |
|     64 | A 조건부 UPDATE |     260 (238~347) |   46.3 |  240.1 |  289.1 | 통과                     |
|     64 | B 비관적 락     |     304 (218~305) |   43.3 |  133.5 |  160.0 | 통과                     |
|     64 | C 낙관적 락     |        21 (21~25) | 1047.6 | 1134.4 | 1157.6 | **탈락**                 |
|     64 | D Redis Lua     | **424 (410~449)** |    1.1 |  171.8 |  195.3 | 통과                     |

- D는 두 worker 수 모두에서 A와 범위가 겹치지 않았습니다. 중앙값 기준 16 worker에서 1.50배, 64 worker에서 1.63배입니다.
- D의 p50이 1 ms 안팎인 이유는 재고 소진 뒤 거절 요청이 MySQL에 가지 않고 Redis에서 끝나기 때문입니다.
- A와 B는 64 worker에서 범위가 겹쳐 차이가 불명확합니다.
- A는 worker를 16에서 64로 늘리자 성공 처리량이 373에서 260으로 낮아졌습니다. 같은 행의 lock 대기열이 길어진 결과로 추정합니다.

### spread: 1,000개 SKU에 분산

spread는 재고가 소진되지 않아 모든 시도가 성공합니다.

| worker | 전략            |               성공/s | p50 ms | p95 ms | p99 ms | hard gate |
| -----: | --------------- | -------------------: | -----: | -----: | -----: | --------- |
|     16 | A 조건부 UPDATE |     1571 (1514~1593) |    9.3 |   15.4 |   25.4 | 통과      |
|     16 | B 비관적 락     |     1512 (1368~1558) |    9.5 |   16.8 |   31.2 | 통과      |
|     16 | C 낙관적 락     |     1552 (1115~1576) |    9.4 |   17.0 |   30.0 | 통과      |
|     16 | D Redis Lua     |     1570 (1325~1648) |    9.6 |   14.7 |   25.3 | 통과      |
|     64 | A 조건부 UPDATE | **2943 (2841~3100)** |   19.4 |   39.2 |   51.1 | 통과      |
|     64 | B 비관적 락     |     2559 (2432~2820) |   22.1 |   45.8 |   59.3 | 통과      |
|     64 | C 낙관적 락     |     2466 (2421~2526) |   22.3 |   48.5 |   65.6 | 통과      |
|     64 | D Redis Lua     |     2780 (2656~2968) |   20.8 |   38.3 |   47.3 | 통과      |

- 16 worker에서는 네 전략의 범위가 모두 겹쳐 차이가 불명확합니다.
- 64 worker에서 A는 B·C보다 범위가 겹치지 않게 높았습니다. A와 D는 범위가 겹칩니다.
- 경합이 낮으면 Redis를 한 번 더 거치는 이점이 없습니다. 병목은 MySQL commit으로 추정합니다.

## 실패한 전략: 낙관적 락

낙관적 락은 hot 64 worker에서 hard gate를 통과하지 못했습니다.

| run |  성공 | 재시도 소진 | 재고가 남았는데 거절 | version 충돌 재시도 |
| --: | ----: | ----------: | -------------------: | ------------------: |
|   1 | 1,825 |       4,175 |                4,175 |              94,955 |
|   2 | 1,791 |       4,209 |                4,209 |              95,728 |
|   3 | 1,784 |       4,216 |                4,216 |              95,462 |

재고 2,000개 중 약 1,800개만 팔렸습니다. 같은 행을 64개 worker가 동시에 갱신해 20회 재시도로도 version 충돌을 넘지 못했습니다. 판매 가능한 상품을 고객에게 거절한 결과이므로 초과 판매와 같은 수준의 결함으로 판단합니다.

hot 16 worker에서도 재시도 소진이 3회 합계 573건 있었습니다. 이 run은 이후 시도가 남은 재고를 모두 팔아서 최종 hard gate는 통과했습니다. 하지만 거절된 573건은 거절 시점에 재고가 남아 있던 요청입니다. 재시도 횟수나 대기 시간을 늘리면 거절은 줄지만 지연이 더 커집니다. 이미 16 worker에서 p95가 231 ms였으므로 더 조정하지 않았습니다.

## 판단

| 전략             | 판단                                                                          |
| ---------------- | ----------------------------------------------------------------------------- |
| A 조건부 UPDATE  | **유지**. 모든 조합에서 hard gate 통과. 분산 경합에서 가장 높거나 차이 불명확 |
| B 비관적 락      | 제외. A보다 명확히 높은 조합이 없고 lock 보유 구간이 더 깁니다                       |
| C 낙관적 락      | 제외. 인기 SKU 경합에서 판매 가능한 재고를 거절                               |
| D Redis Lua gate | 보류. 인기 SKU에서만 성공 처리량 1.5~1.6배                                    |

D를 지금 도입하지 않는 이유는 다음과 같습니다.

1. 이득이 인기 SKU 경합에만 있습니다. 현재 요구사항에는 선착순 판매나 한정 수량 이벤트가 없습니다.
2. 재고의 기준 저장소가 둘이 됩니다. 이번 측정은 정상 경로와 MySQL 실패 뒤 보상만 검사했습니다. Redis 차감 뒤 process가 죽는 경우, Redis 장애, Redis 재시작 뒤 수량 복원, 예약 만료·해제 시 Redis 반영은 측정하지 않았습니다.
3. 보상 로직까지 운영하려면 대사(reconciliation) 작업과 장애 시 fallback 정책이 필요합니다.

한정 수량 이벤트처럼 한 SKU에 요청이 몰리는 요구사항이 생기면 D를 다시 검토합니다. 그때는 위 2번의 장애 시나리오를 먼저 hard gate에 추가합니다.

## 한계

- 이 수치는 로컬 VM 기준선이며 운영 성능이 아닙니다. client JVM과 DB가 같은 물리 host를 공유합니다.
- HTTP·주문 Process Manager를 거치지 않고 재고 예약 SQL만 측정했습니다.
- 수량 1개 예약만 측정했습니다. 여러 SKU를 한 transaction에서 예약하는 경우의 deadlock은 측정하지 않았습니다.
- 3회 반복이라 범위가 넓은 조합(A hot 64 worker의 p95 110~241 ms 등)은 재현성이 낮습니다.

## 재현

```bash
docker compose -f performance/compose.yml up -d mysql redis
RESULT_DIR="$PWD/performance/results/issue-9/strategies" ./performance/run-stock-benchmark.sh

```
